# 工业故障树本体设计

## 1. 设计目标

本设计围绕四个核心业务对象：

```text
部门
文件
设备
故障事件
```

通过文件提供证据，通过设备关联故障，通过统一的 AND/OR 因果表达式表达简单和复杂的故障链。

第一版不引入过多的物理资产层级和领域本体。证据直接保存在关系属性中，后续需要独立审核和复用时再拆分为 `Evidence` 类。

## 2. 本体类

### 2.1 业务主类

| 类             | 含义     | 主要属性                                                                             |
| -------------- | -------- | ------------------------------------------------------------------------------------ |
| `Department` | 部门     | `department_uid`、名称、上级部门、描述、状态                                       |
| `File`       | 数据资产 | `file_uid`、文件名、文件类型、上传时间、存储地址、校验值、版本、解析状态、解析引擎 |
| `Equipment`  | 物理资产 | `equipment_uid`、设备名称、位号、设备类型、厂商、型号、序列号、位置、状态、别名    |
| `FaultEvent` | 故障事件 | `fault_uid`、故障名称、描述、别名、严重程度、故障现象、维修措施、审核状态          |

### 2.2 技术结构类

| 类                 | 含义                     | 主要属性                                                                          |
| ------------------ | ------------------------ | --------------------------------------------------------------------------------- |
| `FaultCauseRule` | 故障结果的因果规则       | `rule_uid`、`effect_fault_uid`、AND/OR 表达式、适用工况、证据、审核状态、版本 |
| `LogicGate`      | 因果表达式投影后的逻辑门 | `gate_uid`、门类型、输出事件、输入事件、证据、审核状态                          |

其中：

- `Department`、`File`、`Equipment`、`FaultEvent` 是业务主类。
- `FaultCauseRule` 用于保存完整的因果逻辑。
- `LogicGate` 用于将因果表达式投影为可查询的知识图谱。
- `Evidence` 第一版作为关系属性保存，不单独成为主类。

## 3. 属性与关系的区分

对象的独立身份、来源和关系应使用节点与关系表示，不应直接存成数组属性。

```text
Department --HAS_EQUIPMENT--> Equipment
Department --OWNS_FILE------> File
```

这样可以分别查询部门设备、文件归属、权限和设备历史。







## 4. 本体关系

### 4.1 组织结构关系

| 关系                   | 源类型         | 目标类型       | 含义               |
| ---------------------- | -------------- | -------------- | ------------------ |
| `HAS_SUB_DEPARTMENT` | `Department` | `Department` | 部门包含子部门     |
| `HAS_EQUIPMENT`      | `Department` | `Equipment`  | 部门管理或包含设备 |
| `OWNS_FILE`          | `Department` | `File`       | 部门拥有上传文件   |


### 4.2 数据资产关系

| 关系                      | 源类型   | 目标类型                                            | 含义                       |
| ------------------------- | -------- | --------------------------------------------------- | -------------------------- |
| `DESCRIBES_EQUIPMENT`   | `File` | `Equipment`                                       | 文件描述某设备             |
| `MENTIONS_FAULT`        | `File` | `FaultEvent`                                      | 文件提到某故障事件         |
| `PROVIDES_EVIDENCE_FOR` | `File` | `FaultEvent` / `FaultCauseRule` / `LogicGate` | 文件为故障知识提供原文证据 |

`PROVIDES_EVIDENCE_FOR` 可包含以下属性：

```json
{
  "page": 38,
  "chunk_id": "chunk-008",
  "section": "4.3 汽蚀",
  "quote": "吸入管漏气且液位过低时，泵发生汽蚀。",
  "review_status": "approved"
}
```







### 4.3 设备故障关系

| 关系          | 源类型        | 目标类型       | 含义                     |
| ------------- | ------------- | -------------- | ------------------------ |
| `HAS_FAULT` | `Equipment` | `FaultEvent` | 设备发生或可能存在某故障 |

示例：

```text
P-101A 离心泵 --HAS_FAULT--> 出口压力不足
```





### 4.4 因果关系

| 关系               | 源类型                         | 目标类型           | 含义                             |
| ------------------ | ------------------------------ | ------------------ | -------------------------------- |
| `HAS_CAUSE_RULE` | `FaultEvent`                 | `FaultCauseRule` | 某故障结果拥有对应的因果规则     |
| `INPUT_OF`       | `FaultEvent` / `LogicGate` | `LogicGate`      | 故障事件或子表达式是逻辑门的输入 |
| `OUTPUT_TO`      | `LogicGate`                  | `FaultEvent`     | 逻辑门输出到结果故障事件         |

`AND/OR` 不作为单条边的属性，而属于 `FaultCauseRule` 中的表达式节点或 `LogicGate`。


## 5. 关系元数据

所有关系建议使用统一的元数据模型：

| 字段                            | 说明                        |
| ------------------------------- | --------------------------- |
| `relation_uid`                | 关系稳定 ID                 |
| `relation_code`               | 关系类型                    |
| `source_uid`、`source_type` | 源对象                      |
| `target_uid`、`target_type` | 目标对象                    |
| `properties_json`             | 页码、Chunk、原文等关系属性 |
| `evidence_ids`                | 独立证据记录 ID             |
| `confidence`                  | 系统计算置信度              |
| `review_status`               | proposed/approved/rejected  |
| `valid_from`、`valid_to`    | 有效期                      |
| `ontology_version`            | 本体版本                    |

关系定义本身应包含：

```text
relation_code
source_types
target_types
direction
inverse_relation
cardinality
required_properties
evidence_required
```

## 6. 简单因果关系

### 6.1 单一原因

```text
A -> E
```

表达式：

```json
{
  "event_uid": "A"
}
```

图谱中可以投影为：

```text
A --CAUSES--> E
```

`CAUSES` 是从因果关系规则派生的查询和可视化关系，不单独维护第二套事实。

### 6.2 OR

```text
A OR B -> E
```

```json
{
  "rule_uid": "RULE-E-001",
  "effect_fault_uid": "E",
  "expression": {
    "op": "OR",
    "children": [
      {"event_uid": "A"},
      {"event_uid": "B"}
    ]
  }
}
```

### 6.3 AND

```text
A AND B -> E
```

```json
{
  "rule_uid": "RULE-E-002",
  "effect_fault_uid": "E",
  "expression": {
    "op": "AND",
    "children": [
      {"event_uid": "A"},
      {"event_uid": "B"}
    ]
  }
}
```

## 7. 复杂嵌套因果逻辑

复杂关系：

```text
(A OR B) AND (C OR D) -> E
```

保存为：

```json
{
  "rule_uid": "RULE-E-003",
  "effect_fault_uid": "E",
  "expression": {
    "op": "AND",
    "children": [
      {
        "op": "OR",
        "children": [
          {"event_uid": "A"},
          {"event_uid": "B"}
        ]
      },
      {
        "op": "OR",
        "children": [
          {"event_uid": "C"},
          {"event_uid": "D"}
        ]
      }
    ]
  }
}
```

投影为逻辑门：

```text
A ──INPUT_OF──> OR-G1
B ──INPUT_OF──> OR-G1

C ──INPUT_OF──> OR-G2
D ──INPUT_OF──> OR-G2

OR-G1 ──INPUT_OF──> AND-G3
OR-G2 ──INPUT_OF──> AND-G3

AND-G3 ──OUTPUT_TO──> E
```

不需要创建名为“A或B组合”“C或D组合”的虚假故障事件。

## 8. Prompt 抽取结果

Prompt 只提取候选实体、设备故障关联和因果规则，不生成正式 UID、Gate UID 和文件元数据。

```json
{
  "entities": [
    {
      "local_id": "eA",
      "class": "FaultEvent",
      "name": "A",
      "description": "故障 A",
      "maintenance_measures": [],
      "evidence": [{"quote": "A 或 B 发生时"}]
    },
    {
      "local_id": "eB",
      "class": "FaultEvent",
      "name": "B",
      "description": "故障 B",
      "evidence": [{"quote": "A 或 B 发生时"}]
    },
    {
      "local_id": "eC",
      "class": "FaultEvent",
      "name": "C",
      "description": "故障 C",
      "evidence": [{"quote": "C 或 D 也发生"}]
    },
    {
      "local_id": "eD",
      "class": "FaultEvent",
      "name": "D",
      "description": "故障 D",
      "evidence": [{"quote": "C 或 D 也发生"}]
    },
    {
      "local_id": "eE",
      "class": "FaultEvent",
      "name": "E",
      "description": "最终结果事件",
      "evidence": [{"quote": "会导致 E"}]
    }
  ],
  "equipment_fault_links": [],
  "relations": [],
  "cause_rules": [
    {
      "effect_local_id": "eE",
      "expression": {
        "op": "AND",
        "children": [
          {
            "op": "OR",
            "children": [
              {"event_local_id": "eA"},
              {"event_local_id": "eB"}
            ]
          },
          {
            "op": "OR",
            "children": [
              {"event_local_id": "eC"},
              {"event_local_id": "eD"}

```

## 9. 核心约束

### 9.1 身份约束

```text
所有正式对象必须有稳定 UID
名称修改不能改变 UID
equipment_tag 在租户内唯一
文件校验值用于重复检测
部门、设备和文件不能靠名称作为外键
```

### 9.2 结构约束

```text
关系的源类型和目标类型必须符合关系定义
故障因果图必须是有向无环图
故障树只能有一个顶事件
一个故障规则必须指向一个结果故障
AND/OR 节点至少有两个子节点
Gate 只能有一个输出
同一表达式树中不能有重复输入
```

### 9.3 证据约束

```text
正式因果关系必须有证据
证据 quote 必须是原文精确子串
证据必须关联到有效文件
删除文件不能静默删除已被正式知识引用的证据
```

### 9.4 审核约束

```text
候选关系不能直接发布
实体合并必须人工确认
AND/OR 结构必须人工确认
关系修改必须保留历史版本
```

## 11. 最终结构

```text
Department
├── HAS_SUB_DEPARTMENT → Department
├── HAS_EQUIPMENT ─────→ Equipment
│                        └── HAS_FAULT → FaultEvent
│                                          └── HAS_CAUSE_RULE → FaultCauseRule
└── OWNS_FILE ─────────→ File
                         ├── DESCRIBES_EQUIPMENT → Equipment
                         └── PROVIDES_EVIDENCE_FOR → FaultEvent
                                                        / FaultCauseRule

FaultCauseRule
└── expression = EventRef | AND(...) | OR(...)
                         ↓
                     LogicGate
                         ↓
                 INPUT_OF / OUTPUT_TO
```

核心原则：

> **业务对象用类和属性表示；对象关联用有类型的边表示；因果关系统一用递归 AND/OR 表达式表示；AND/OR 表达式投影为 LogicGate；文件和证据负责支撑正式知识。**
